# SPRINT-15-02-02 — Motion MCP, resources, transactions e histórico

**Fase:** 15 — Agentes Futuros
**Grupo:** Motion Design e Motion MCP
**Status inicial:** PLANNED
**Dependências:** `SPRINT-15-02-01`, `SPRINT-09-03`, `SPRINT-09-06`, `SPRINT-09-07`
**Superfície principal:** tools semânticas, inspeção seletiva, autorização e revisões
**Bloqueia o MVP de agentes:** não

## Objetivo

Expor a engine por um MCP autorizado, com poucas tools semânticas, resources limitados, transaction coordinator, optimistic concurrency, idempotência, auditoria e Undo lógico compartilhado.

## Escopo

1. Implementar transporte MCP Streamable HTTP, `tools/list`, `tools/call` e resources; manter `stdio` somente no harness local.
2. Implementar `motion.project.*`, `motion.composition.*`, `motion.document.apply`, `motion.layer.inspect`, `motion.timeline.*`, `motion.asset.*`, `motion.catalog.list`, transaction tools e job contracts.
3. Reutilizar schemas de `motion-contracts`; não criar schemas inline nas rotas.
4. Derivar workspace/audience/scopes da identidade autenticada e da delegação.
5. Aplicar ownership, capability, budget, approval e resource scope antes de mutar.
6. Implementar baseRevision, conflito explícito, idempotency key e resposta estruturada.
7. Implementar OperationGroup, undo, redo/restore e label humano/IA.
8. Implementar resources com fields/include/depth/limit/cursor/checksum para economia de contexto.
9. Redactar segredos e inputs sensíveis de traces/logs.
10. Criar contrato de erro com recovery/next step para o agente.

## Arquitetura envolvida

```text
McpRemoteClient -> motion-mcp (Streamable HTTP) -> policy/identity -> motion application service
                                      -> document/revision/history repository
```

O MCP não chama stores, renderer ou banco diretamente. O servidor não conhece worker físico; render é job posterior.

## Critérios de aceite

- Um cliente MCP consegue executar a PoC estrutural sem UI automation.
- `tools/list` não expõe effect/3D/asset capability não habilitada.
- `inspect` padrão retorna resumo limitado e permite buscar apenas a layer/timeline solicitada.
- Batch com 20+ operações é atômico e resulta em uma nova revisão/Undo.
- Repetição da mesma idempotency key não duplica entidade nem revisão.
- BaseRevision antiga retorna conflito e preserva o trabalho atual.
- Token de outro workspace ou recurso é recusado e auditado.
- Undo de IA não desfaz edição humana concorrente.
- Approval requisitada permanece `WAITING_APPROVAL` até decisão confirmada.

## Testes

- JSON-RPC/MCP conformance de `tools/list`, `tools/call` e resources.
- Testes de schema, auth, audience, scopes, ownership, delegation e budget.
- Idempotência, replay, timeout, transaction expiration, rollback e double commit.
- Conflitos entre dois atores e Undo/Redo em branch.
- Teste de token/context compaction comparando inspect seletivo e documento completo.
- Fuzz de IDs, operation types, depth/limit/cursor e payloads desconhecidos.

## Definition of Done

- Tool catalog e resources documentados e versionados.
- Auditoria mostra actor, workspace, resource, run/task, trace, base/new revision e result.
- Nenhum binário, segredo ou path arbitrário é enviado ao LLM.
- Lint, typecheck, build, testes de contrato e migration limpa passam.
- O relatório registra topologia do transporte e integração pendente, se o serviço ainda não estiver hospedado.

## Estados e verificação de experiência

O cliente MCP cobre `loading`, `empty`, `error`, `success`, `WAITING_USER`, `WAITING_APPROVAL`, conflito e rollback/expiração. Cada erro devolve código, motivo e próximo passo; o protocolo não apresenta commit ou aprovação antes da confirmação da API.
